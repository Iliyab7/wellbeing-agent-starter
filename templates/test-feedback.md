# Pilot feedback — share only a synthetic or redacted copy

Do not put real health information, participant identity, calendar contents, credentials
or private checkpoints in a public issue. Describe a bug with invented data that reproduces it.

- Package version/commit:
- Host product and observed mode (no account identifier):
- Test date:
- Capabilities actually verified:
- Scenario and synthetic input:
- Expected behavior:
- Actual behavior, with safe evidence:
- Result: passed / failed / blocked / not tested:
- Was a user-visible action actually executed, or only proposed/prepared?
- Did it preserve uncertainty, goals, scope and attention preference?
- Next change or question:

For native host orchestration, include safe evidence for acceptance scenarios A19/A20
in [the acceptance guide](../docs/acceptance-tests.md): instruction/skill attachment,
actual dispatch and report receipt, targeted revision, verified closure, and truthful
invalidation/cancellation. Operator-entered ledger state alone is not proof of host execution.

For private participant feedback, ask what was useful, what felt burdensome, and what
they would change. Do not treat silence as approval or a better metric as proof of benefit.
